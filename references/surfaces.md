# B 层：表面适配（Surfaces）

哲学内核（A 层）跨表面共享；**表现与 chrome 必须按表面翻译**。

官方 Apple 原则（仅适用于理解精神；非 Apple 表面不得声称 HIG 合规）：

- https://developer.apple.com/design/human-interface-guidelines/design-principles
- https://developer.apple.com/videos/play/wwdc2026/250/

可扩展：新增表面时，补一行对比表 + 一节「习惯来源」，仍走「精神借用、本地惯例」规则。

容器先按 `platform-router.md` 定。下表每一列是一种容器，不能互相代替。

## 容易混的几对

- **手机没有默认系统。** 只说手机时先问 iOS 还是 Android。iPhone 不包含 iPad，也不包含 Android。
- **网站不是安装的桌面应用。** 网站活在浏览器标签里，窄了是 mobile web。Windows 或 macOS 应用有自己的窗口栏和命令位置。
- **扩展不是网站。** 弹窗做一件事；完整书库、账户和低频设置进选项页或另开的网页。
- **Windows 不是「桌面」。** macOS、Windows、Linux 各有窗口习惯。Linux 还要再分 GNOME 与 KDE；没说就问，或看项目已经用的 libadwaita / Kirigami。
- **框架不是皮肤许可证。** Flutter 文档区分「适应空间」和「换成该平台可用的布局与输入」。目标是 iOS 就用 iOS 的导航，即使代码是跨平台的。
- **只做手机就停在手机。** 不要自行加上桌面或网页方案。

## 翻译规则（A → B）

### 规则 1：意图不变，容器变

同一 Purpose / IA 意图，换成该表面的导航壳与主操作位置。  
例：「查看列表 → 打开详情 → 编辑」在 iOS 用推入导航；在 macOS 用列表+详情分栏；在扩展里可能拆成「弹窗列表 → 选项页详情」。

### 规则 2：精神借用，不借皮肤

非 Apple 表面可借用：

- 清晰目的、用户控制、晚请求权限、宽恕、层级清楚、细节诚实

不可借用（作为默认外观）：

- iOS Tab Bar / Large Title / 过多圆角卡片堆叠冒充「高级」
- 把 SF Symbols 审美当 Windows/扩展的唯一图标语言而不考虑系统图标

输出中必须写一句，并把括号换成这次的表面：

> 本方案在 {Android|网页|Windows|Linux|扩展} 上借用 Apple 设计原则的精神（Purpose、Agency 等），不声称符合 Apple HIG；控件与导航遵循 {Material|WCAG 与网页惯例|Fluent/WinUI|GNOME 或 KDE|浏览器扩展} 惯例。

### 规则 3：平台优势优先（Flexibility）

| 表面 | 优先发挥 |
|------|----------|
| iOS 手机 | 快速触达、手势、专注单任务 |
| iPadOS | 分栏、拖放、指针精度 + 触控 |
| Android 手机 | 系统返回、底栏或顶栏的既有位置、48 dp 触控目标 |
| 响应式网页 | 同一页面随视口重排；键盘与窄屏触控都要能完成主任务 |
| macOS | 键盘、多窗口、菜单发现性、深度工作流 |
| Windows | 多窗口、命令栏、键鼠、系统主题。不是其他桌面的代称 |
| Linux | 所选桌面环境已经教给用户的头栏、菜单和快捷键 |
| Extension | 宿主上下文、最小打扰、即时动作 |

### 规则 4：密度与会话长度匹配（Simplicity）

扩展弹窗：默认 **一个主任务**；次要能力进选项页。  
桌面：允许更高信息密度，但层级仍须一眼可读。  
手机：先主任务，渐进披露。

### 规则 5：权限按表面模型翻译（Responsibility）

- Apple：用途说明 + 情境化请求 + 系统设置深链
- Android：运行时权限在用到该能力时再问；拒绝后主任务要有降级，而不是照抄 iOS 的文案框
- Windows：能力声明 + 系统隐私页引导 + 应用内解释
- 网页：浏览器权限提示；在动作发生时再要，不用安装式的权限清单冒充
- Linux：跟随该桌面的门户（portal）或系统设置，不发明第二套系统对话框
- Extension：`permissions` / optional permissions；在用户触发需要该能力的动作时再请求；避免安装时一口吃光

### 规则 6：一致性按表面边界定义（Familiarity）

- 先与 **该 OS/浏览器惯例** 一致  
- 再与 **自家产品在该表面内** 一致  
- 最后才考虑跨表面「品牌感」（颜色/语气），而非复制布局

### 规则 7：可扩展表面模板

新增表面 `X` 时填写：

1. 输入方式与会话长度  
2. 导航壳与设置入口  
3. Familiarity 权威来源（官方 UX 指南链接若有）  
4. 与本产品其他表面的翻译差异  
5. 明确：是否声称任何 HIG/其他合规（默认否，除非该表面就是 Apple）

## 多表面产品策略

1. 先写 **共享设计合同**（Purpose、对象、成功标准、非目标）  
2. 再为每表面写 **落位差表**（同一功能：入口在哪、主按钮在哪、设置在哪）  
3. 禁止「一份线框打天下」；允许共享组件库，但 chrome 分叉  

差表只列这次真正要做的表面。最小字段示例：`功能 | 主表面 | 其他表面 | 备注`。

用户范围是只做手机时，差表里不要出现桌面或网页列。
