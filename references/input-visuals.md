# 视觉输入解读：截图 vs 线框

截图与结构化线框/画框均为一等公民输入。纯文本需求可跳过本文件。

**锁定规则：** 当 **截图 + 线框同时存在** 时：

1. **先对齐线框意图**（结构、主次、路径）  
2. **再用截图做现实校验**（已实现、系统 chrome、密度、偏差）  
3. 在「风险与翻译备注」写出 **意图 vs 现实** 差距表  

---

## 输入类型识别

| 类型 | 特征 | 当作 |
|------|------|------|
| 截图 | 照片/PNG 真实 UI、系统状态栏、真实字体与控件 | **现实** |
| ASCII 盒 | `+--+`、`| |`、缩进盒 | **意图线框** |
| 标注区域 | 「顶部工具栏」「列表区」「主按钮」等标签 | **意图** |
| 正式线框 | 灰盒、占位文案、无品牌抛光 | **意图** |
| 精修 mock | 高保真视觉 | 默认当 **现实或提案现实**；若用户声明是「愿景」则当意图并注明 |
| 外部参考截图 | 别人的产品、奖项作品、截图库（Mobbin 等）里的画面；常伴「像这个」「参考这个」 | **外部参考**：不是本产品现实，也不是本产品意图；只提取可命名的手法 |

若无法判断：先假设「有标签的是意图，像素真实的是现实」，并在输出中写假设。

---

## 如何读线框（意图）

按序提取：

1. **表面暗示** — 是否画出 Tab/侧边栏/菜单栏/扩展弹窗比例？若无，用用户声明的表面补全。  
2. **区域清单** — 每个盒的名称与职责（导航 / 内容 / 主操作 / 辅助 / 状态）。  
3. **层级** — 哪一块最大、最上、最对比：那是视觉主任务。  
4. **路径** — 箭头、编号、「步骤 1/2」；无则从主 CTA 反推。  
5. **缺失** — 空态、错误、权限、设置入口是否未画（常见）→ 列入待补。  
6. **标签歧义** — 不清楚的标签先短确认；无法确认时列假设。

ASCII 解读提示：

```text
+------------------+
| nav              |  ← chrome
+------------------+
| list             |  ← 主内容
|                  |
+------------------+
| [primary CTA]    |  ← 主操作
+------------------+
```

输出时应把意图总结为：`区域表 + 主路径 + 显式非目标（线框没画的）`。

---

## 如何读截图（现实）

按序提取：

1. **系统 chrome** — 状态栏、标题栏、手势条、浏览器工具栏、扩展弹窗边界。  
2. **已实现导航** — 当前 Tab/侧边栏选中项、栈深度线索（返回标题）。  
3. **密度与层级** — 是否拥挤、主 CTA 是否淹没、对比是否足够。  
4. **文案与状态** — 加载中/空/错误是否诚实；权限拒绝是否可见。  
5. **平台一致性** — 控件是否像该表面原生；是否假 iOS 皮。  
6. **可访问线索** — 目标过小、仅靠颜色区分、截断文案等风险。

截图 **不能** 单独证明产品意图；只能证明「现在长这样」。

## 双输入对齐流程（必须）

```text
线框意图 ──总结──► Intent Model（IA + 主路径 + 区域职责）
                         │
截图现实 ──对照──► Reality Check
                         │
                   Gap List（多/少/错位/平台违和）
                         │
                   设计合同采用 Intent；用 Gap 驱动改版建议
```

差距表模板：

| 项目 | 线框意图 | 截图现实 | 建议 |
|------|----------|----------|------|
| 主导航 | … | … | 保留意图 / 或因平台约束改壳 |
| 主 CTA | … | … | … |
| 设置入口 | … | … | … |
| … | … | … | … |

**冲突裁决：**

- 意图清晰且符合声明表面 → **改现实就意图**  
- 意图违反表面硬约束（如扩展弹窗塞满桌面级 IA）→ **改意图就表面**，并在备注说明  
- 意图模糊 → 先补问或列假设，再落合同

## 外部参考截图（别人的产品）

线索：Eian（@EianLu）X 文章强调先看「已经上线运营的真实产品」，并要求看到好东西时「用一句话说出它到底好在哪」。

1. **单独归类**：不进 Intent Model，也不进 Reality Check；在输出里写「外部参考」。  
2. **复述 + 命名**：「我看到的是……」，再说出 1–3 个具体手法（例如「结果数字放大并锚定在底部」），不用「高级」「干净」这类空词。  
3. **对原则**：每个手法写出它服务的原则（或 `eight-principles.md` 里的 UX 定律）。  
4. **按表面翻译**：参考来自其他平台时，只借意图；按 `surfaces.md` 规则 2「精神借用，不借皮肤」处理。  
5. **不照抄**：不搬品牌色、插画、专有布局；概念稿只借气质，不当落位证据。  
6. 写法模板见 `reference-library.md` 规则 2。

## 仅有截图

1. 反推可能意图（带置信度）  
2. 用八原则诊断现实问题  
3. 提出「重设计合同」——明确哪些现实可留作 Familiarity，哪些必须改  

## 仅有线框

1. 补全未画状态与权限  
2. 按表面做落位翻译（可能线框画的是错误壳）  
3. 给线框级修订，不要求精修  

## 仅有文本

1. 跳过视觉对齐  
2. 直接合同 → 落位 → 结构（可用 ASCII 产出线框级结构）  

---

## 参考图输出标准（教练侧）

- 默认交付 **线框级方向**：区域、标签、主路径箭头、状态标注
- 不把没有出处的 pt、圆角写成合同
- 双输入时：可并排「意图结构 | 现实问题 | 建议结构」三列文字或 ASCII
- 用户另外要求可视草稿时，线框仍然先出；能打开的稿件按 `visual-drafts.md`。不要把这一节理解成拒绝出图  

---

## 常见误读（避免）

1. 把截图里的临时实验 UI 当成最终意图  
2. 把线框里的占位拉丁文当真实文案层级  
3. 忽略截图中的系统安全区/扩展裁切，提出不可实现的布局  
4. 双输入时只「修图」不「护意图」  
5. 对 Windows/扩展截图仍按 iOS 间距与导航开药方
