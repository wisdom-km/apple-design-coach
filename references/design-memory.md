# 项目里的视觉记录

平台记在 `.apple-design-coach/context.md`。视觉方向记在项目已经在用的那份设计文档里。两份文件不要各写一套会打架的色和字。

## 进入项目时先找

项目根清楚时，按这个顺序看，找到就沿用：

1. 用户点名的设计文档、截图或组件。
2. 根目录的 `DESIGN.md`。
3. 已经在记录视觉的 `PRODUCT.md`，或 `design-system/**/MASTER.md`。
4. 项目里现成的颜色、字体、组件（样式文件、设计 token）。只读并遵守，不另起一份平行记录，除非用户同意加一份摘要，并且摘要指向原文件。

没有这些，而且用户也没描述过方向：走 `direction-choice.md`。有了确认过的方向：下次「再出设置页」用同一套字、色和密度，只改这一屏的结构。只有用户明确要重做，或两份记录互相冲突时，才重新打开方向。

项目根不清楚（不知道文件该写到哪个仓库）时，不写任何设计文件。把决定放在回复里，并写「未写入项目」。

## 谁说了算

| 问题 | 以哪份为准 |
|------|------------|
| 表面、系统、范围、问不问平台 | `.apple-design-coach/context.md` |
| 已确认的字、色角色、密度、组件语气 | 上面找到的那份视觉记录 |
| 两份对平台或方向说法不同 | 先问。不要静默覆盖 |

`context.md` 只加一行指针，例如 `visual_record: DESIGN.md`。不要把整套色值再抄进 context。

## 新建或更新

新项目、方向已经确认、而且根目录清楚、还没有视觉记录时：写一份短的 `DESIGN.md`。

已经有记录时：先重读，再改那一份。保留用户写的字段和你不认识的标题。在文件里加一句这次改了什么、依据是用户确认还是教练在用户委托下代选。不要为了套模板删掉原有句子，也不要在用户没同意时整页换成另一套品牌。

建议包含，已有字段不要删：

```markdown
# Design record

- status: confirmed
- surface:
- direction_name:
- confirmed_by: user
- visual_record_note:

## Color roles
## Type
## Density
## Components
## Placement
## Unknown
```

`confirmed_by` 只有两种诚实写法：`user`，或 `coach-because-user-delegated`。不要把代选写成用户已确认。

色值是项目决定就标明项目决定。官方数字仍要有出处。不要把私人事实写进本 skill 仓库。不要为了记录去跑脚本、建注册表或安装别的设计引擎。
