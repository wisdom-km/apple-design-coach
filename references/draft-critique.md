# 草稿之后的短评审，并且真的改

完整可视草稿出来之后，用最多 5 条可执行的检查看一遍。发现能在已确认方向里改掉的问题，就改草稿，不要只交一份意见。

检查同时看 A 层和 B 层。每次只挑和这张稿有关的，凑不满 5 条就少写。

| 看什么 | 原则 | 不过关时 |
|--------|------|----------|
| 内容边：同角色的前缘还在不在；背景和文字是不是两条边 | Familiarity、Craft | 改负责边距的那一层。说明样式盖住应用段落时，先拆开宿主 |
| 行列与字：数字后缘、基线、长标题和完整金额有没有撞在一起 | Craft | 改列或换行。全文仍要能读到 |
| 分组节奏：同组是不是比组间紧；密度是不是这套方向 | Simplicity | 调组距。不要改成大卡片、大留白或海报大数字 |
| 层级重量：第一眼是不是主任务；危险操作是不是仍不同形 | Purpose、Agency | 降次要重量。不删操作 |
| 状态情境：同一组件在主帧、说明宿主和状态里是不是同一几何；导航还在不在该平台 | Familiarity | 复用骨架。平台位置不对就改回去，不能换成另一套系统 |

每条只写四样：位置与可见现象、负责的关系、改动、同位置再看的证据。可以少于 5 条。只看主帧通过、后面的状态被说明样式改掉，不算过。编辑次数、全部标成通过、自称 Craft、设计记录里已经写了 token，都不是这一项的证据。看不清就写尚未核对和原因。最终看正常比例的彩色画面。灰阶只作辅助。

宿主里如果真的列着 `aesthetic-coach` 或 frontend-design，可以用它的问法帮这次评审，并写明用了哪一个。没有就用上表。不要为了评审去安装 Impeccable、Hallmark 或其他引擎。

## 状态与布局（同一次自检）

仍从上面的表里挑，最多 5 条。和状态有关时按任务决定画什么，不另做一张长清单。

- 列表或会失败的读取：空白、加载、失败和恢复要出现在稿上，不能只写在句子里。
- 任务不用敏感能力：不画权限页。要用权限：稿上有拒绝，以及重试或降级，主任务还能做完。
- 离线、未保存、不可逆：只有这个任务里有才画。
- 长中文、合适的字号放大、窄宽度：用来看会不会截断或把按钮挤出屏幕。不必每种状态各做一份放大成品。
- 稿旁写覆盖说明。每一项只标已画、不适用（带原因）或尚未核对（带原因）。
- 数字和名单来自用户，或标成示例数据。不编真实指标。
- 在 HTML 里放大字号不是 iOS 动态字体，也不是安卓权限弹窗的真机测试。

## 改稿

- 改的是已确认方向里的层级、对比、落位和可恢复性。
- 原有的功能、文案和链接都留着。难做的功能不能悄悄拿掉。
- 用前后两稿，或一张精确的改动清单，让人看出动了哪几处。
- 换整套视觉方向，或增删产品功能，先问用户。评审本身不是重做许可。
- 看过渲染或截图，就按看到的问题改画面，并写出看得见的前后差：字重、换行、对齐、控件外形、空态密度、外壳谁更响。编辑次数、多写的注释、声明用了 Craft、静态检查通过，都不算这一项合格。
- 第一眼若是说明书或粗设备框，先改这一帧的外壳，再补状态说明。
- 没渲染，就写「未对照成图，以下是对结构的检查」。
- 浏览器里打开 HTML 的截图不是可用性测试，不是真机，也不是某家 CLI 已经照做的证明。手写的示例稿同样不是一次真实会话的成绩。

思路来自公开文档里的「先计划再自查」和「精修留下原功能、重做才换外观」。出处见 `source-provenance.md`。这里不复制那些仓库的手册，也不运行它们的脚本。
