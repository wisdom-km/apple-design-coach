# 可视草稿（在合同和信息架构之后）

默认交付仍是设计合同、落位和结构线框。用户明确要视觉草稿、mockup、原型或「看一下长什么样」时，再增加一份**可以打开看**的草稿。

不要只给绘画提示词，也不要只给 ASCII，然后把那一份称为已经出的视觉稿。ASCII 是结构线框。二者都需要时，先给结构，再给视觉稿。

---

## 顺序

1. 设计合同和功能落位已经写完（或沿用上下文文件里没变的部分）。
2. 方向未定：按 `direction-choice.md` 停在 2–3 个轻量选项。文字说明要标明不是已渲染预览。
3. 方向已确认或项目已有记录：按 `aesthetics.md` 和 `design-memory.md` 写明字体、间距、密度、颜色角色和层级。
4. 再做完整视觉稿。视觉稿不引入合同里没有的主任务，也不改已选平台的导航。
5. 稿能看之后按 `draft-critique.md` 检查并改一版。
6. 在稿旁注明：这是设计草稿，不是该平台的原生实现，也不是真机测试。

用户说「只要设计、不要写产品代码」：可以做独立的草稿文件，不要开始建产品工程，不要改产品源码。用户连草稿文件也不许写：把单文件 HTML 放进回复，并写「未落盘」。

设计工作不授权实现整个应用，也不授权把项目数据送到一个新的外部服务。要做这两件事，先问。

---

## 先看这次真正有什么工具

只使用当前会话工具列表里确实存在、且说明文字就是用来生成或渲染图像的工具。不要假设存在 GenerateImage、Superdesign、Figma 或浏览器。

| 实际能力 | 交付 | 必须写明的话 |
|----------|------|----------------|
| 能写文件，用户能打开 | 无外部依赖的单个 HTML | 「浏览器打开的是设计草稿，不是真机，也不是应用已实现」 |
| 工具列表里确有图像生成 | 一张静态图，并遵守已写的合同 | 「生成图，不是该系统的截图」 |
| 两者都没有 | 结构线框 | 「本轮没有可视草稿，只有结构线框」 |

没有图像工具时，不要说「如果我有 GenerateImage 就会……」来假装有过可视化。HTML 草稿就是可视草稿的正经回退，只要它能被打开。

本仓库的 `examples/drafts/` 是这种 HTML 草稿。它们用系统字体和页内样式，没有外部脚本、字体或图片请求。里面的名单和金额是示例数据。

---

## 稿件验收

一份合格的视觉草稿：

- 能离线打开，双击 HTML 即可，不需要构建步骤。
- 页首或页尾能看出：哪个平台、哪种容器、示例数据。
- 主任务、主操作、设置和危险操作的位置与落位说明一致。
- 颜色和间距若不是官方数字，稿上或旁边标明「示例决定」。
- 按任务把该出现的状态画进稿里，并在旁边写覆盖说明：已画、不适用（原因）或尚未核对（原因）。列表要能看到空白、加载、失败和恢复。没有权限需求就不画权限页。不必把每种组合都做成一份成品。
- 多目标时，每个目标各有自己的 chrome，不把同一张图改个标题。

浏览器里给 HTML 拍的图，用来给人检查这张草稿。它不能当作 iPhone、Android、Windows 或 Linux 真机测试。

---

## 和旧说法的关系

本 skill 仍然不是像素级规范生成器：不输出没有出处的「圆角 12、间距 8」当作交付合同。

它也不再把「用户要看界面」拒绝成只能描述线框。结构线框是默认；可视草稿是被要求时的下一步。二者不要混名。
