# 项目诊断与落地

用于已有项目评估、具体建议和授权后的实现。只调查本次任务需要的路径。

## 建立一张小项目地图

读取仓库指令和工作区状态，保留用户修改。查看 README、依赖与运行配置，找到主入口、路由/导航、目标页面、共享组件和样式 tokens；再沿相关事件处理器追踪保存、取消、错误、权限与恢复逻辑。检查已有测试与启动脚本，使用实际存在的命令。

记录：`产品/用户 | 主任务 | 运行平台与最低版本 | 技术栈 | 必须保留的能力 | 证据位置 | 可运行程度`。没有对应证据的项写未知，不为了填表遍历整个仓库。

例如：`浏览器记账工具 | 新建账单后保存 | Windows 上的 web | React | CSV 导入、批量分类 | README、BillingForm、tokens | 尚未启动`。不能从 React 推出 iOS，也不能从 Windows 推出必须改用 WinUI。

## 诊断顺序

先沿用户要完成的任务走一遍：入口 → 输入/选择 → 提交 → 结果 → 失败恢复。找到最先阻碍任务的环节，再评估层级、导航、文案、可访问性和装饰。没有运行环境时，用静态路径分析，明确这是风险判断。

关注已经有效的部分：保留能工作的导航、组件、键盘交互和业务能力。频率未知时，不武断把导入、批量操作、专家功能藏进设置。提供条件化选择，例如“若每周导入，保留账单页入口；若仅首次迁移，放入初始化流程”。

优先级按 **影响 × 发生情境/频率 × 证据可信度** 作定性判断。实现成本影响排期，不会让严重问题变得不严重；不编造分数、转化率提升或用户研究结果。

## 一条建议的实例

> **P1 · 保存失败反馈不清，恢复能力待确认。** 用户描述提交后只出现“错误”；未提供代码，尚不能确认输入是否丢失。建议在表单内保留输入、给出可理解的失败原因和重试入口；只有确认确实保留时才显示“输入已保留”。这体现 Agency 与 Craft，也符合 [WAI 表单反馈](https://www.w3.org/WAI/tutorials/forms/notifications/) 的方向。验收：输入一条账单，模拟保存失败，检查字段仍在、错误被读屏获知、重试成功且没有重复记录。以上为待执行验证。

有项目时把“表单”换成实际组件路径，指出复用的错误提示组件和现有保存服务；不凭空写 `src/components/BillingForm.tsx`。

## 实施时

用户要求修改后，在现有组件/状态模型中完成最小有效修复。优先复用按钮、对话框、错误展示、间距/颜色 tokens 和已有恢复能力。给旧平台保留可用路径，不为了外观升级最低版本或引入新 UI 框架。

用用户可观察的结果验证：失败时保留输入、键盘能完成操作、错误语义可感知、重试不重复提交。代码质量检查和构建不能代替交互检查；截图不能代替读屏/键盘检查。按项目环境选择现有测试、浏览器、模拟器或真机，缺失环境明确列出。

避免用测试匹配建议的固定措辞。新增回归测试应守住行为，例如模拟服务拒绝后表单值不清空，而不是检查建议是否出现“Agency”。

## 合适的报告规模

- 小问题：结论、理由、改法和验收，一两段足够。
- 项目诊断：简短项目理解；按优先级给建议；最后列必要的未知和验证边界。
- 实施：说明实际改动、影响的路径、运行过的检查和未覆盖情境。
- 没有访问权限/材料：根据用户描述给暂定建议，明确需要什么证据才能进一步定位。不能声称已经检查了仓库。
